# GitHub Issue タスク起票

思いつきをそのままissueに書くのではなく、いくつかの観点で人間と一緒に理解を深めてから起票するスキル。目的は**着手前に曖昧さを削っておくこと**——後でClaudeや自分が着手したとき、判断に迷う余地をできるだけ減らしておく。

判断するのは常にユーザー。このスキルは観点を提示して理解を深める補助であり、Claudeが単独で優先度や合否を決めるものではない。

**前提**: `gh` CLIがこのマシンにインストール・認証済みであること(`gh auth status`で確認)。無ければ `brew install gh && gh auth login` を案内する。

## Step 1: アイデアを聞く

やりたいこと・直したいことをユーザーから聞く。既に会話の中で十分語られていれば聞き直さなくてよい。

## Step 2: 既存issueとの重複を確認する

`gh issue list --search "<キーワード>"` で似た既存issueが無いか確認する。見つかったら、新規に起票するか既存issueを更新するか、その場でユーザーに確認する。

## Step 3: 観点で理解を深める

以下の観点を、儀式的な採決としてではなく**会話の中で**確認していく。すべてを毎回フルに聞く必要はない——タスクの性質に応じて、明らかに関係ない観点は軽く流してよい。

- **Engineer観点**: 技術的に実現可能か。既存の構成(Next.js App Router、`src/app/` のルーティング、`src/components/`、`src/lib/posts.ts` と `posts/` のMarkdownによるブログ、Sass/Tailwindの使い分け)と整合するか。Server ComponentとClient Component(`"use client"`)のどちらで書くべきか。ざっくりの工数感。技術的負債にならないか
- **PM観点**: スコープは適切か(大きすぎるなら分割を提案する)。他タスクとの依存関係はあるか。優先度(must/should/want)はどれか
- **PO観点**: 受け入れ条件(完了の定義)を明確にできるか。サイトの訪問者(採用担当・読者など)にどんな価値があるか
- **Designer観点**: 既存のデザイン(配色・余白・フォント・レスポンシブ)と一貫しているか。スマホ幅での見え方、アクセシビリティ(コントラスト・alt・キーボード操作)に影響しないか

## Step 4: 起票内容をまとめる

Step 1〜3を踏まえて、以下の形でドラフトを作る。

- **タイトル**: 番号は付けない(issue番号は`gh issue create`が自動採番する)。先頭にタスクの種類を示すprefixを付ける(`feat:` 新機能、`fix:` 不具合修正、`docs:` ドキュメントのみ、`chore:` その他雑務。このリポジトリのコミットも同じprefixを使っている)。例: `feat: プロダクト詳細ページにSNSリンクを追加する`
- **背景・なぜやるか**
- **受け入れ条件(完了の定義)**
- **スコープ**: 含むこと / 含まないこと
- **優先度**: must / should / want のいずれか
- **実装メモ**: Engineer観点で出た技術的な考慮点(あれば)
- **検討メモ**: Designer観点などで話し合った内容(あれば。懸念とその解消内容は残す)

## Step 5: 確認する

ドラフトをそのまま提示し、`AskUserQuestion` で「この内容で起票する / 内容を直す / やめる」を確認する。直す場合はStep 3〜4に戻る。

## Step 6: issueを作成する

1. `gh label list` で既存ラベルを確認する。優先度(must/should/want)に対応するラベルが既にあれば使う。**無ければラベルを勝手に新規作成しない**——本文に優先度を書くだけに留め、ラベル運用を始めるかはユーザーに確認する
2. Step 4のドラフトをMarkdownの本文に整形する(見出しは`##`程度で十分)
3. `gh issue create --title "<タイトル>" --body "<本文>"`(該当ラベルがあれば`--label`も付ける)で作成する
4. 作成したissueのURL・番号をユーザーに伝える
